## 2. 验证方法与结果

### 2.1 流程与规则（回放核对器）

对每局 dump 以期望状态机逐步回放，断言：

1. 首事件为庄家弃牌（庄家 14 张先打）；
2. 摸牌轮转：上家打牌后由下家摸（除非声明取走）；
3. 吃只能声明上家弃牌且成顺子；碰成刻；杠成四同；
4. 副子后由声明者打牌；杠后从牌尾补牌（`drawn.source=kong`）；
5. 暗杠只在自己摸牌后、补杠前（`kongPromoted`→meld(kong=2)→杠尾补牌→打牌）；
6. 终局收束：和牌局末事件为 `win`、流局局为 `exhaustive` 且牌墙余 0；
7. 牌张守恒：终局清点（各家手牌＋副子＋未声明取走的弃牌＋牌墙余）＝136，任一牌 ≤4 张；
8. 点和放铳者＝最后弃牌者；`winnerHand` 与 `hands[winner]`/和牌张关系一致。

**结果：4355 局全部通过，无一违例**（含 1 例庄家开局暗杠的合法首序列——种子 2075：庄家摸第 14 张即暗杠→杠尾补牌→弃牌）。核对器自身的多轮修正均为核对器 bug，已在工具注释中记录。

### 2.2 动作合法性与协议鲁棒性（对真实服务端探测）

每用例独立起服务端（种子 6），逐项发送非法输入：

## 3. 问题清单（按严重度分级）

### 阻断（玩不下去/结果严重错误）

无。

### 规则错误（与国标不一致）

**R1（高发）｜未达 8 分起和线的和牌照常判和并结算**
- 现象：随机对局 272 个和牌中 149 个（55%）总番 <8（如种子 13：无字＋边张＝2 番），引擎照常判和，结算照常支付（放铳者付 2＋8、其余各付 8，胜者＋26）。
- 规则依据：98 规则/WMO 均有 8 分起和线——未达 8 分的和牌不是有效和牌（竞赛规则中属错和，应判罚或流局处理）。项目仅在计分输出 `eligible` 标志，无人执行。
- 复现：`npm run e2e 13`（确定性：座位 3 和牌，2 番未达线，dump.score.eligible=false，settlement 照常非零）。
- 归属建议：**需决策**——起和线把关注引擎（和牌声明时把关，需在声明时即时计分）还是桌面/对局层（拒绝 win 动作或判无效和）。涉及 GX-2/GX-3/GX-4 边界调整（GX-2 边界曾把起和线推给 GX-3，但 GX-3 只输出判定）。
- 备注：真人玩家不会像随机驱动那样频繁报低番和牌，实际游玩中发生率远低于 58%，但规则正确性缺口是实质的。

**R2｜全求人与自摸共现——已修复（GX-3 v1.1），复验通过**
- 现象（基线 8f71ecd）：随机对局 272 个和牌中 22 个同时计入「全求人（6）」与「自摸（1）」（如种子 6、1067）。
- 规则依据：98 原文「全求人：全靠吃牌、碰牌，**单钓别人打出的牌**和牌。**不计单钓**」——和牌张自摸与定义冲突；原实现为无出处的有意编码。
- 修复与复验：GX-3 @ 1a302c8 将全求人限定为点和/抢杠和，并新增「全求人不计单钓将」冲突项；复验（合并树 + 300 局新口径样本）：种子 6→6 番（无全求人）、1067→4 番（无全求人），全求人×自摸共现 0、全求人＋单钓将共现 0。**关闭**。

**R3｜单钓将漏计（口径过严）**
- 现象：胡牌张以将位参与、但同牌在明组中另有出现（全牌共 3 张）时不计单钓将。102 个全求人和牌中 10 个漏计（含种子 93）（如种子 93：手牌 4万 单张吊将，234万 明组中另有一张 4万，漏计单钓将，总番 8 实应 9）。
- 规则依据：单钓将定义「和牌时手中只有一张牌，以此牌作将成和」——听牌型以暗牌形状判定，与明组中同牌无关。实现按「全牌中恰 2 张」判定（detectors.go waitKind）过严。
- 影响：漏计 1 分可能翻转起和线判定（R1 修复后影响放大）。
- 复现：`npm run e2e 93`（确定性）。
- 归属建议：GX-3（waitKind 口径修正为暗牌形状判定）。

### 体验问题（能玩但不该这样）

**E1｜--dump 非原子写出，消费方偶发读到截断 JSON**
- 现象：300 局扫描中 6 次（约 2%）dump 文件已存在但内容尚未写完（"Unexpected end of JSON input"）。根因：cmd/gameserver writeDump 用 `os.WriteFile`（open-truncate-再写），文件先存在、内容后到；e2e 以「文件存在」为完成信号。
- 影响：GX-4 自带 e2e 偶发红、以及一切按「存在即完整」取用 dump 的验证/工具链（含本验证）。
- 复现：循环运行 `npm run e2e 92` 直至失败（实测 360 次内复现）。
- 归属建议：GX-4——写临时文件后 `os.Rename`（原子落盘）；e2e 侧改为「可解析」为完成信号。

### 记录项（待议）

**N1｜bad_version 拒绝后服务端主动关闭连接**：协议版本不符无法继续，断连合理；其余 11 类错误均保持连接。观察行为，无需动作。

**N2｜dump 字段语义注意点（消费方须知）**：① `hands[winner]` 在点和/抢杠局不含和牌张（该张留在河），`winnerHand` 含——以 `winnerHand` 为计分输入（本项目已如此）；② 无副子座位的 `melds[s]` 为 `null`（omitempty 语义）；③ score.fans 的 `value` 是分项合计（表值×count）。

**N3｜自摸计边/坎/钓**：docs/score-rules.md 已记录的已知偏差（规则要求自摸牌单独摆放才计听牌型），按裁定维持。

**N4｜抢杠和路径在随机对局中不可达**：4355 局随机驱动（种子 1–4300）＋400 局偏置驱动（优先碰/杠/补杠——反而 0 和牌，作废）未出现一次抢杠成和（他家恰好听被补杠之牌的概率过低）。引擎层有定点单测覆盖（TestPromoteKongRobbed）；**协议/桌面层的抢杠成和全链路未见实局证据**。建议后续以脚本化定向局补证（需可指定牌局的驱动器），或接受引擎单测＋协议测试为足够证据——由 Assignee 裁定。

**N5｜随机对局流局率约 88%**：无策略自动座（随机合法动作）下的必然结果，非规则错误；真人游玩的和牌率将远高于此。记录以免误读统计。

## 4. 结论

- **流程层（发牌→摸打→吃碰杠→终局收束）**：4355 局回放核对零违例，非法动作 12/12 正确拒绝，E2E 确定性成立——**一局全流程正确**。
- **计分层（番种识别/取最优/结算公式）**：3512 局机械核对零违例；番种语义人工核对发现 R2、R3 两处与规则定义不一致，R1 为起和线执行缺口。
- **原型可用性**：Linux 同构侧全流程可跑通；Windows 实机人工试玩见 §2.4。
- 问题清单：0 阻断、1 规则错误（R1，待裁决）＋2 已修复（R2/R3，复验关闭）、1 体验问题、5 记录项。
